# DataGuard Québec — Architecture & Repository Audit

**Repository:** `Akumo961/DataGuard-AI`  
**Branch audited:** `main`  
**Audit date:** 2026-08-26  
**Audit phase:** Phase 1 — repository audit  
**Audit posture:** evidence-first; no production-readiness claims are inferred from documentation alone.

## 1. Executive summary

The current repository is a small research/prototype codebase, not an enterprise privacy platform. The repository contains a FastAPI prototype, a Gradio UI, several intended ML components, sample/configuration artifacts, three empty notebooks, and a small test/demo surface. The repository is public and the default branch is `main`.

The most important finding is not merely that enterprise functionality is missing: several core files are internally inconsistent or structurally broken. In particular, `src/preprocess.py` and `src/data_loader.py` contain their intended Python implementations inside string assignments rather than defining the classes at module scope; `src/models/pii_detector.py` has the same pattern. `src/utils/validators.py` is malformed/truncated. `config.yaml` is actually a Python setup script rather than YAML. The API compensates for import failures with fake fallback implementations. Therefore the documented ML pipeline is not currently an executable, reproducible production pipeline.

The repository also contains zero-byte model artifacts, zero-byte data artifacts, zero-byte result artifacts, and empty notebooks. The README claims 95%+ PII detection accuracy and a 90% reduction in manual review, but the repository does not contain reproducible evaluation evidence supporting those claims. The training script itself uses dummy compliance training data and expects a `labels` field that does not match the sample training-data schema generated by the setup script.

The current architecture therefore has to be treated as a prototype foundation to be rebuilt, not incrementally marketed as an enterprise product.

## 3. Current architecture

The intended architecture is approximately:

```text
Gradio UI
   |
   v
FastAPI API
   |
   +--> FileDataLoader --> text extraction / OCR / Whisper
   |
   +--> TextPreprocessor --> regex PII / spaCy NER / tokenizer
   |
   +--> RiskAssessor --> heuristic score
   |
   +--> ComplianceAnalyzer --> hard-coded framework lists
   |
   +--> intended transformer models
```

The actual executable architecture is less complete. `src/api/main.py` catches import failures and installs local fallback classes, including a simplified regex detector and simplified risk assessor. The intended router is commented out. The production execution path is therefore not guaranteed to exercise the intended model/data pipeline.

There is no persistent application database, no tenant boundary, no user identity model, no authorization model, no job queue, no object-storage abstraction, no audit ledger, no compliance-control database, and no PIA workflow.

## 4. Current capabilities verified from code

### 4.1 API

The FastAPI application exposes:

- `/`
- `/health`
- `/test`
- `/analyze/text`
- `/analyze/file`

Text analysis accepts an untyped `Dict[str, Any]`. File analysis writes the upload to a temporary file and passes it to the document loader.

The API does not implement authentication, authorization, tenant isolation, API versioning, request IDs, structured audit records, rate limiting, security headers, configurable CORS, or persistent analysis records.

### 4.2 UI

The current UI is a Gradio application with text analysis, limited file analysis, and an API test tab. It is explicitly prototype-oriented and directly calls the API. It is not an enterprise frontend architecture.

The file UI only advertises TXT/PDF/DOCX despite the backend containing intended support for additional formats.

The UI renders API-derived values into HTML strings without an explicit output-encoding strategy. This must be redesigned rather than extended blindly.

### 4.3 PII detection

The intended detector combines regex patterns with spaCy NER and an intended BERT token-classification model. The currently visible regex taxonomy is small: email, phone, SSN, credit card, IP address and address.

The requested enterprise taxonomy is substantially broader and must become configurable.

### 4.4 Risk scoring

`RiskAssessor` uses static weights for PII types and static context/file modifiers. The result is explainable in a basic sense but is not a validated risk model and does not incorporate the full set of requested factors such as exposure scope, retention, encryption, purpose, data location, organization policy, regulatory framework, confidence, and quantity in a defensible way.

### 4.5 Compliance

The current code contains hard-coded lists labelled GDPR, HIPAA and CCPA. These are not machine-readable legal controls, do not carry versions or authoritative references, and do not represent an auditable compliance framework. They must not be treated as legal conclusions.

## 5. Broken functionality and high-confidence defects

### P0 — Core import/runtime integrity

1. `src/preprocess.py` assigns the entire intended implementation to `preprocess_py = """..."""`. The classes `TextPreprocessor` and `ComplianceAnalyzer` are therefore not defined at module scope.
2. `src/data_loader.py` similarly assigns its intended implementation to `data_loader_py = """..."""`; `DataLoader` and `FileDataLoader` are not defined at module scope.
3. `src/models/pii_detector.py` similarly assigns its intended implementation to `pii_detector_py = """..."""`; `PIIDetectorTrainer` is not defined at module scope.
4. `src/utils/validators.py` is malformed and contains a truncated/broken string after the email regex. It cannot be considered a reliable importable validator module.
5. `src/api/main.py` catches import errors and substitutes fake classes. This hides broken dependencies/code instead of failing safely and can create false confidence about which implementation is executing.

### P0 — Configuration integrity

`config.yaml` is not YAML. It contains a Python setup script. Code in `DataLoader` and `train.py` expects YAML keys such as `supported_formats` and `models`, so those paths cannot operate against the current file as written.

### P0 — ML reproducibility

The repository contains zero-byte model artifacts:

- `models/compliance_classifier.pkl`
- `models/risk_model.joblib`

There is no committed trained BERT/transformer model directory, tokenizer artifact, model card, dataset manifest, reproducible evaluation output, or model checksum.

### P0 — Evidence integrity

The following are zero-byte:

- `data/processed/features_vectors.npy`
- `data/processed/tokenized_data.pkl`
- `data/raw/compliance_rules.yaml`
- `data/raw/pii_training_data.json`
- `data/raw/sample_documents.txt`
- `results/compliance_report.html`
- `results/model_metrics.json`

Consequently, the repository does not contain the data/evidence needed to substantiate the documented ML results.

### P0 — Training pipeline mismatch

`train.py` expects each PII training item to contain `labels`, while the setup script's sample training-data generator creates an `entities` array. The two pieces are incompatible.

The compliance training path explicitly uses dummy demonstration data rather than a validated dataset.

### P1 — API security

`src/api/main.py` configures `allow_origins=["*"]`, wildcard methods, wildcard headers and credentials enabled. This is unsafe for production and violates the requested security posture.

The application binds to `0.0.0.0` without an authentication boundary. There is no rate limiting or abuse protection.

### P1 — Upload security

The API accepts uploads without invoking the existing `FileHandler` validation helper. It does not enforce the intended MIME/extension/size checks at the API boundary, does not use a safe upload policy, and does not implement malware scanning or decompression-bomb protections.

The temporary file is always given a `.txt` suffix in `main.py`, which can interfere with correct type handling.

### P1 — Error handling / information leakage

The API returns raw exception text to callers. Debug `print()` statements include the first 100 characters of submitted text and detected PII. This is unacceptable for a privacy platform because sensitive input can appear in application logs.

### P1 — Path and lifecycle assumptions

Multiple scripts assume the current working directory is the project root. Operational behavior is therefore fragile. Temporary file handling, model loading, OCR, and Whisper model initialization are not isolated worker processes.

### P1 — Unused/duplicated API implementation

`src/api/routes.py` duplicates much of the analysis behavior but is explicitly not included by `main.py`. This creates two competing API designs and increases maintenance and security risk.

## 7. Privacy-by-design assessment

The current implementation does not provide persistent privacy governance capabilities. There are no models/workflows for purposes, data sources, recipients, storage locations, retention, safeguards, owners, remediation, approvals, incidents, or PIA/EFVP evidence.

The target product must treat privacy metadata as first-class data and separate it from raw document content. Raw sensitive documents should not be retained by default merely because an analysis was performed.

For Québec positioning, the platform must support both private-sector and public-sector governance profiles rather than collapsing them into a single generic "GDPR/HIPAA/CCPA" label. Québec public bodies are subject to the Act respecting Access to documents held by public bodies and the Protection of personal information, while the private sector is governed by the Act respecting the protection of personal information in the private sector. The Commission d'accès à l'information identifies governance, responsible roles, privacy-impact assessments, access/rectification, incidents, retention/destruction, and lifecycle protection as important areas. These must be represented as configurable controls and evidence workflows, not automated legal conclusions.

## 8. Québec compliance gap analysis

The repository currently has no machine-readable Québec framework. This is a major gap because the target market requires a configurable framework capable of distinguishing:

- Québec private sector.
- Québec public sector.
- Health and social-services contexts where applicable.
- Canadian privacy frameworks.
- International frameworks such as GDPR and CCPA/CPRA where a customer needs them.

The product should encode control intent, evidence requirements, applicability and verification status. Legal references must be verified against authoritative sources before publication and versioned so a framework update does not silently rewrite historical assessments.

Relevant official starting points for the implementation team include the Commission d'accès à l'information's Law 25 overview, its public-sector guidance, and the official Légis Québec text of the public-sector access/privacy statute. The CAI explicitly states that its explanatory web material does not have the force of law; authoritative legal text must therefore be the final source used for legal verification.

## 13. Database and persistence assessment

There is no application database implementation. Although SQLAlchemy and PostgreSQL drivers appear in requirements, no SQLAlchemy models, Alembic migrations, repository layer, transaction boundary, or PostgreSQL schema is present in the audited tree.

The target architecture requires PostgreSQL for transactional metadata and governance records, with object storage for controlled document payloads where retention policy permits. Redis should be introduced only for concrete needs such as job coordination, rate limiting, caching or ephemeral state.

## 14. Background processing assessment

Document extraction, OCR, Whisper transcription, and transformer inference are currently synchronous/in-process operations. This is unsuitable for reliable enterprise workloads.

A worker architecture is required for long-running analysis, with explicit job states, retries, idempotency, resource limits, cancellation behavior, and tenant-aware scheduling.

## 24. Definition of success for the transformation

DataGuard Québec should not be considered enterprise-ready until an independent engineer can clone the repository, install pinned dependencies, run the automated tests, start the services, authenticate, create/select a tenant, upload only permitted synthetic/sample data, execute an asynchronous analysis, inspect explainable PII findings and risk factors, complete a PIA workflow, create remediation items, inspect a complete audit trail, generate an evidence report, and verify tenant isolation — without relying on hidden manual steps or fake fallback implementations.

For ML, a release must include reproducible evaluation evidence. For compliance, the system must provide configurable controls and evidence workflows while explicitly preserving human/legal review. For government deployment, residency, security architecture, operational controls, procurement requirements and contractual obligations must be assessed separately for each implementation.

## 25. Audit conclusion

**The repository is a viable conceptual starting point but is not currently an enterprise privacy platform.** The correct strategy is a controlled rebuild around the useful ideas already present — PII detection, document extraction, risk scoring and FastAPI — while replacing the fragile prototype plumbing with a secure, typed, testable, multi-tenant architecture.

No code functionality has been represented as complete merely because a placeholder, class, or README section exists. This audit should be treated as the baseline for Phase 2.
